# Native adapter contract 1.0

This package is an offline engineering contract, not an enabled integration. All actions default to HOLD. `catalog.v1.json` assigns every enumerated action to one native owner, API boundary, idempotency key and readback strategy. `contract.py` is a synthetic in-memory contract harness; it performs no I/O to applications and supplies no production durability or authorization.

## Authority and sources

Source baseline: `reference/components/component_registry.json` CP055–CP061, CP063, CP076, CP141/CP144/CP147; `reference/workflow_catalog.json`; `AGENTS.md`; `docs/decisions/ADR-001-ENGINEERING-AUTHORITY.md`; `docs/security/CONTAINER_AND_HOST_BASELINE.md`. These are design evidence, not upstream API compatibility receipts. No release numbers, endpoint routes, provider identities or supported combinations are invented here.

Mautic owns contacts, suppression/permission and campaigns. WordPress owns web publication. Postiz owns social schedules. OpenProject owns business/editorial/budget/publication approval; GitHub engineering status cannot grant it. ResourceSpace owns original assets and rights. Matomo owns website analytics and SerpBear owns rank observations. Asterisk owns channels and bridges; providers own their external delivery receipts. Activepieces remains the cross-application orchestrator. PostgreSQL records operational intents/receipts only: adapters never write native application tables, even to repair a timeout.

## Versioned interface

Use the F04 `urn:marketing-v7:runtime:event-envelope:1.0`, `approval-reference:1.0` and `action-receipt:1.0` contracts. The envelope retains schema_version, event_id, source, event_type, occurred_at, received_at, client_id, workflow_id, correlation_id, idempotency_key, authority_ref, nullable approval_ref/channel_eligibility_ref, payload_ref and default_outbound_state=HOLD. F04 validation is a prerequisite, not implemented again here. Root must validate the integrated F04/F05 candidate. The adapter tests freeze the actual F04 action-receipt key vector; delivery evidence additionally records a read-only check against the supplied F04 candidate.

Adapter request 1.0 has exactly schema_version, adapter, action, account_ref, action_key, expected_revision (nullable for create/read), payload_ref and outbound_state=HOLD. The action key is exactly `sha256:` followed by 64 lowercase hexadecimal characters (bare hex is rejected), the F04 SHA256 key for the compact UTF8 JSON tuple of client_id, source_system, source_event_id, action_scope, approved_revision. Namespace the durable reservation by adapter and account_ref. Bind action_scope to the native destination and operation; changing account, payload digest, approval/revision, destination or operation requires a newly authorized intent. Payload references resolve only through the trusted evidence store; never fetch arbitrary input URLs. Optimistic update/withdraw operations require the current native revision/lock token where supported; if unavailable, serialize and compare a native readback before applying a reviewed change.

The harness records HELD -> SUBMITTED -> UNKNOWN before reconciliation, consistent with the F04 transition subset it models. NOT_OCCURRED releases the active reservation while retaining a deduplication tombstone; OCCURRED retains it. Neither permits resubmission. The harness fingerprints the complete request and rejects reuse of a key with changed intent. Runtime implementations must atomically reserve the key before submission, retain a receipt across crash/restart, and persist request payload/approval digests in the reservation. This in-memory harness is neither a production ledger nor an exactly-once claim. No native idempotency support is assumed: qualification must prove provider/native key scope, retention and conflict semantics. Without native deduplication, reconcile by recorded native ID or supported external correlation lookup before resubmission; inability to distinguish absent from pending is UNKNOWN.

Map results into F04 receipts with the same event/correlation/action identities, attempt, destination, evidence_ref and nullable native object reference. Native IDs are opaque, account-scoped strings. SUBMITTED or ACCEPTED only establishes native admission, never publication/delivery. Completion needs native/provider readback. Preserve original timestamps, source receipt and stale/partial flags; stale/missing analytics cannot be treated as zero.

## Error and callback rules

`ERRORS` distinguishes invalid request, authentication, permission, policy hold, optimistic conflict, not found, unsupported capability, rate limit before submit, transient before submit, timeout after submit, ambiguous response, malformed callback and stale evidence. Rejected input/authentication is not retried. Refreshing credentials is an operator action. Rate limits respect verified Retry-After and a bounded retry budget only when non-submission is proven. A network timeout after possible submission is UNKNOWN, with HOLD and retained reservation. Reconciliation produces OCCURRED (native ID plus evidence, reuse existing result) or NOT_OCCURRED (authoritative absence evidence, held pending new authorization); neither creates retry authority. A 404 alone may reflect eventual consistency, wrong account or expired retention and is not proof of absence.

Callbacks enter a trusted, release-specific verification adapter before parsing/applying state. It validates the documented signature or authenticated transport against the *original* bytes, correct method/path/audience where required, selected account/key rotation, timestamp window, provider event identity and expected native object. Source IP alone and a payload flag are insufficient. Never accept an unsigned callback because its format resembles a valid one. For products without authenticated callbacks, mark them unsupported and poll the native API using scoped credentials. Persist the callback event ID and resulting receipt atomically so replay after restart is inert. Unknown object/account, tampering, replay, stale/future time or verification failure cannot authorize any action. `CallbackProof` is returned by a trusted verifier configured outside request data; the synthetic test verifier is not a vendor protocol implementation. Even a valid callback is receipt evidence, not human approval, consent, or retry permission.

Common release profile evidence must include upstream release/API documentation digest, version/edition, native dependencies and worker inventory, scoped capability/read/write tests, retry and callback proofs, image/package identity where applicable, storage/restore tests and rollback/held-resume procedure. These missing facts block live enablement, not completion of this offline contract. Any newly desired action requires a reviewed contract revision, not a fallback to native SQL or an arbitrary HTTP operation.

## Operator runbook

1. Keep outbound HOLD and real egress/credentials absent. Validate F04 schemas, adapter request and owner/action allowlist; reject unknown version/action.
2. Check a qualified release profile and least-privilege account. Fetch fresh native permission/rights/approval state. Bind revision, destination, assets and channel eligibility; a Boolean supplied in a request is not approval.
3. Reserve the account-scoped action identity durably and record approval/payload digests. Resolve any earlier UNKNOWN before submission. A trusted runtime gate, outside this package, controls any release from HOLD.
4. Submit only via the qualified native API/worker. Record native request/job ID before acknowledging acceptance. On uncertain response, retain reservation and reconcile with a bounded observation window; escalate unresolved state.
5. Authenticate callbacks or poll, deduplicate durably, verify account/object correlation, and append evidence-backed F04 receipts. Never turn a callback into a new outbound command.
6. On restore, hold all queues/schedules, restore native files and databases coherently, reconcile previously submitted effects and verify current approval/consent before a separately authorized resume.

Run `python -B contracts/adapters/test_contract.py` and `python -B -O contracts/adapters/test_contract.py`. Tests are synthetic and offline; production API, worker behavior, signature schemes, external effects and independent acceptance are NOT_RUN.
