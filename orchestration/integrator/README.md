# F13 reviewed integration policy candidate v1

This is the **reviewed-policy alternative** allowed by F13/issue41, accompanied by a nonauthorizing host consistency guard. It is an implementation candidate awaiting independent review and ROOT execution of its tests. It does not install a merge queue, launch a controller, open PRs or perform GitHub/SDK effects. `reviewed-policy.v1.json` is a versioned contract, not an approval. Every guard result remains `decision=HOLD`, `effect_authority=NONE`, including a consistent positive.

## Host guard API and exact boundary

`policy_guard.assess(base_root, candidate_root, result_bytes, *, expected_binding, host_facts, policy)` compares an externally authenticated current binding, independently collected host facts, a sanitized worker-result projection and two **complete stable exported trees**, outside worker reach. It has no CLI, subprocess, Git, network, database or mutation adapter. It works on qualified POSIX descriptor-relative filesystems; unsupported platforms fail closed. It does not establish OS isolation by role instruction or create the trusted worktree itself.

Complete-tree inventory and remote evidence have separate budgets. The inventory allows 2,048 total entries (files plus directories), 8 MiB per regular file and 32 MiB per export. The canonical reviewed repository at the preceding F13 revision has 1,424 tracked files plus 68 directories, totaling 21,515,651 bytes; `ISSUE_BROWSER.html` is 5,223,092 bytes. The immutable base has 1,420 files plus 66 directories and 21,465,090 bytes. These caps leave 556 entry slots and about 12 MiB aggregate headroom for that candidate; reaching a cap remains bounded, and exceeding it holds. Future growth requires a separately reviewed policy change, never an omitted file, subset export or unbounded walk. The inventory fixture reproduces every canonical path and size using synthetic bytes; it is not the actual repository content or an authenticated host export.

Remote raw source pages remain limited to **2 MiB each and 8 MiB combined**, independently of the larger inventory. Sanitized result size stays 256 KiB, with 64 pages per source kind and 4,096 records; increasing repository capacity does not enlarge remote proof input. Descriptor-relative cap-plus-one discovery, pending-sibling accounting and final reread remain unchanged.

The host must independently authenticate and pin repository/task/fence/input/base/head/tree, actual author/reviewer identities, selected model/runtime, review freshness, required native checks, source routes and complete historical findings. It must generate the sanitized result projection after validating the original `schemas/agent-result.schema.json` and removing bearer lease fields. The projection has exactly task_key/fence/input_sha256/base_revision/status/summary/changed_paths/artifacts/tests/blockers; tests are host-enriched records with binding and output digest. It is deliberately not a replacement worker schema or a document accepted directly by `LocalController.finish`.

The guard reads actual files with no-follow descriptor traversal, checks regular/unlinked file type, modes, complete inventories, content hashes, entry/file/total bounds and observed before/after identities. It computes the diff and candidate manifest itself. This task has a closed four-file route: this README, policy JSON, guard and `tests/integrator/test_reviewed_policy.py`. No author-declared scope can widen it. Any unowned/protected change, deletion/rename, link/hardlink/special file or traversal/ambiguous path holds and requires human escalation. The JSON's protected sets are minimum central boundaries, not a permission list for future tasks.

Host source observations cover complete review, issue-comment, inline-comment, thread, check, native, history and finding pages. Every page carries contiguous terminal pagination, raw UTF8 plus computed raw digest, exact current binding and unique raw-record identities/digests. The guard compares raw records to their declared manifest and requires a disposition for every observed finding. It rejects duplicate/unknown/incomplete data. The host must collect these from actual authenticated routes with full pagination and typed semantics, not assemble worker-provided “trusted” facts. The guard cannot authenticate caller JSON or a UUID, detect omitted remote pages not observed by its caller, or interpret arbitrary review prose as an approval. Thus its positive is **consistency only**, never merge eligibility.

The host review projection requires distinct actual author/reviewer identities, a completed whole-candidate fresh gpt-6.1-sol/MAX assessment with zero open P0-P3 findings, exact binding and host-verified time window. Current exact-head required check names/App IDs/status/conclusion and unique check IDs must agree with the host-approved profile. Host test output/result hashes must agree with actual worker result and files. Every prior finding retains its source digest plus current regression/re-review binding. Actual GitHub Codex is additional and deduplicated; confirmed unavailability is not technical approval or a fabricated native APPROVED review. Model assessment, native review, human protection and trusted acceptance are separate authorities.

Callers cannot turn a positive into effect authority. Hashes establish consistency, not origin. The guard exposes only redacted reason codes, computed manifest digest and consistency/escalation status; it never echoes result text or credentials. Errors and unknown observations remain HOLD. It performs no writes. Even with stable fd-based reads there is a small non-atomic interval after observation; the existing trusted owner must recollect and revalidate current raw sources/gates immediately before any authorized effect. An untrusted writable export cannot be made safe by these checks alone.

## Existing-owner integration and recovery runbook

1. Confirm current STOP/cutoff, prerequisite ancestry, capacity/budget, exact lease/fence/input, owner and protected paths. Keep the trusted source/worktree/Git metadata, hooks/config, credentials, control ledger and journal outside the agent's mounts. The isolated worktree and external access boundaries require measured host evidence; collaboration role boundaries alone do not prove them.
2. Host-export complete base/candidate trees, independently compute Git head/base/tree and actual diff/content, validate the full original result, then form the sanitized projection and host facts. Run this guard as an additional consistency check. A failure blocks this candidate; a positive still holds for existing-owner review and authority.
3. Obtain independent fresh-context whole-source MAX assessment at exact candidate identity; preserve all prior raw findings and current fix ancestry/regression/re-review. Obtain current exact-head CI and actual native rules/reviews/thread state through the existing verifier. An author's check IDs or favorable text are data. No self-review, temporary waiver, fake check success or fabricated native approval is allowed.
4. Only the existing trusted integrator creates its isolated integration worktree outside agent reach, copies allowed verified regular files, disables untrusted Git hooks/config, commits and opens a PR through its already admitted protocol. Serialize main updates under its original lock. Refresh expected head/base/tree/test/review/source digests after rebase or conflict resolution; **any** change invalidates previous result, review, test and check evidence. Re-run applicable tests and fresh review, never transplant old green evidence.
5. Re-read full volatile sources/current native/CI/finding gates after slow immutable reads and immediately before admission. Submit the normal expected-head merge through the original sole journal/mutation owner, with exact operation/request envelope and original budgets. No bypass or self-native approval. Timeout/error is UNKNOWN: preserve pending, reconcile exact remote head/parents/main outcome and request identity before existing supported adoption; never blindly resubmit. This guard cannot adopt, retry or charge/refund anything.
6. Preserve original attempt/journal/raw reviews and verify actual merge receipt/parent/main ancestry/current checks before the trusted controller records acceptance. Distinguish candidate head from actual merge commit. A worker result or “merged” log never unlocks dependents. Crash/replay must use the same owner, fence and original operation and positive remote proof; unknown state retains reservations and locks. Current fresh completion review and original at-effect proof are distinct. Do not renew stale approval by backdating or a global clock patch.

A postmerge append-only receipt does **not** retire the original active attempt. The current owner intake records stage25 retirement/exclusive-path/single-effect/reconciliation work as unfinished and an authenticated compact/default-spaces wire-envelope mismatch as open. The finite producer compatibility/version binding also requires explicit protected review. F13 neither fixes nor masks these existing integration limits; no dependent release or next-merge readiness is claimed.

ROOT must run the complete suite at the exact commit, obtain independent fresh MAX, current CI and perform its authorized publication loop.

A reviewed-policy deliverable does not qualify an executable distributed merge queue. That later claim needs an independently admitted existing-owner disposable end-to-end pilot: measured isolated worktree/access boundary, hooks disabled, serialized conflict/rebase with fresh tests/review, actual PR/current check/native/merge readback, uncertainty reconciliation and trusted acceptance. No old merge is replayed as a new pilot. No deployment, real native qualification,576-case credit, G02 clearance or full DoD is implied. No new queue, secret store, private ledger, SDK acceptance, production operator or orchestration platform is introduced.
