# F11 local controller wrapper v1.1

This is a source implementation candidate. It reuses `tools/scheduler.py` and its SQLite tables, claim ordering, resource accounting, path/explicit-lock conflict rules, fencing and budget settlement. It does not replace Activepieces, create a distributed scheduler or launch workers. No real controller database was opened during implementation. Tests are supplied for root's isolated executor and have not been run by this author.

## Invariants and changes

`local.LocalController` subclasses the reference scheduler. Claims retain its `BEGIN IMMEDIATE` transaction covering current states, capacity, cost, path prefixes, explicit locks, attempt count and lease issue. Strict finite/nonnegative resource validation rejects booleans and unknown resource dimensions. Configuration is deep-copied and fingerprinted so caller mutation cannot alter authority after construction. Graph/policy changes still require the reference scheduler's explicit migration boundary.

Expiry is quarantine, not cancellation. Wrapper mutations execute `_expire` before a savepoint. A rejected operation rolls back its own writes, reruns expiry, and commits quarantine. Thus stale/malformed finish or heartbeat cannot roll back ORPHANED state or free its reservations. Unknown cost remains conservatively charged at the reservation; trusted overruns stop new dispatch. REVIEW retains path/explicit locks; running/orphaned work retains resource and cost reservations. Safe result submission releases resources only after process and outcome reconciliation.

A SQLite trigger creates a durable launch-attempt reference in the same transaction as the bundled scheduler claim. The trusted launcher binds a process/job with `bind_process` before external work. An existing process binding cannot be replaced. `finish` and `reconcile_orphan` require exact identity, matching bound reference, independently verified positive termination and external-outcome reconciliation. An uncertain remote submission or absent callback is not positive proof. If the controller crashes before process binding, the attempt remains present with a null process reference. Null never proves that nothing launched: an independent verifier must supply the exact launch reference, task/fence/input/base, explicit no_launch_confirmed=true and effects_reconciled=true with attributable evidence before orphan recovery. Such proof is recovery-only and cannot finish a candidate. No provider process is started or killed by this module.

`finish` validates the complete nested result shape, field types, SHA256 formats, finite costs, path scope and duplicate artifact/path entries. Unknown nested keys are rejected; this is deliberately stricter than the legacy result schema's permissive nested objects. A separate trusted candidate revision plus file-manifest digest binds the submitted result. The private ledger retains a digest of the sanitized result and candidate identity. Bearer lease fields are omitted from stored results and status projections. Sensitive content scanning and actual file/manifest verification remain mandatory in the trusted integrator before calling this method; syntactic digests are not provenance.

`accept` requires the current REVIEW attempt, exact fence/input/base, current graph/policy, candidate revision, manifest and sanitized-result digest plus positive independent review/check receipts. A previous attempt's receipt cannot accept a newer candidate. `candidate_revision` binds the reviewed head; `revision` retains the actual merge commit, which can differ for normal or squash merges. This follows `tools/verify_merge.py`; the trusted ingestion adapter must preserve both fields and enrich the receipt with current attempt/manifest identity. Only CODE_MERGED or independently substantiated SANDBOX_QUALIFIED levels are supported here; no manual production approval or staging/production claim is implemented. Exact-head GitHub evidence verification remains the existing trusted verifier's responsibility. The author cannot accept their own result. Replaying acceptance is rejected.

## Caller boundary

All these methods are privileged local controller APIs, not agent endpoints. A dictionary containing `terminated: true`, an `evidence_ref`, or a string `trusted_admission_ref` is not authentication. The trusted caller must verify attributable launcher/reaper, provider readback, file scope/digests, reviewer identity and receipts outside untrusted worker input. Workers receive only their fenced task packet; they cannot import this controller against the private ledger or call `accept`/reconciliation. DB and WAL/SHM files must remain on one local durable filesystem with restricted OS access, excluded from agent mounts and publication. Never use NFS/SMB for this SQLite file.

No real lease credential, private packet or live state is embedded in source or fixtures. Tests create synthetic packets through temporary scheduler instances and discard them. Public logs should contain task/fence/state and redacted evidence references, never lease tokens or raw result content. Existing reference `record` omits the token and result storage is sanitized, but the trusted caller remains responsible for redacting its own exceptions and logs.

## F08 admission and F04 alignment

F08's `docs/orchestration/capacity/check_dispatch_inputs.py` is reused for non-fixture claims. Live mode is the default, requires the supplied dispatch inputs and measurements to pass that checker, and additionally requires an externally verified admission reference. The checked inputs are immutable for an instance. These checks establish structural input presence only; the caller still verifies freshness, approved capacity mapping, provider enforcement and G02 authority. The supplied F08 inputs intentionally remain HOLD, so unattended live claims stay denied. `config/capacity.approved.json` is intentionally absent; no replacement approval or invented limit is added.

`fixture_only=True` is an explicit test mode for temporary synthetic databases, not permission to launch agents. Its mode is recorded durably and a database cannot be reopened in the other mode. Do not point fixture mode at an existing controller. Both modes only issue local fenced records; this module contains no launch adapter.

F04's immutable client/source/action/revision identities and UNKNOWN/HOLD semantics remain authoritative for business operations. F11 does not reinterpret business action receipts as process termination or engineer acceptance. Native provider APIs, current permission checks and their atomic operational ledgers remain separate. This wrapper's process/outcome proof is engineering control-plane evidence, not a fabricated F04 business receipt.

## Review remediation and task evidence requirements

The trigger is named `f11_atomic_claim` and inserts the attempt while the reference scheduler updates RUNNING/fence. Claim rollback rolls back both records; committed claims survive restart even before `bind_process`. The new launch_ref column requires a reviewed migration for an older wrapper database. This task does not run that migration or access any live ledger. A no-launch proof is an externally authenticated fact about the precise launch attempt, not a fallback when a process ID cannot be found. Once any process is bound, only positive termination plus outcome reconciliation can release it.

All tasks must declare a supported `kind` and the exact current graph authority `independent reviewer + trusted integration controller`. Missing or unknown authority/kind is rejected. Foundation, component, implementation, test-authoring, preservation and provider tasks require CODE_MERGED with `verified-github-merge`; an omitted evidence_level means that code requirement, never arbitrary evidence. Verification and integration require SANDBOX_QUALIFIED with `verified-independent-executor`; an omitted level for these runtime kinds means sandbox only, and the graph's SANDBOX_QUALIFIED_ONLY is enforced. Contradictory explicit requirements fail closed. A code merge alone cannot qualify verification, and sandbox evidence alone cannot complete code delivery. Selection and human-gate/manual work cannot be claimed/accepted through this adapter and require their separately reviewed authority paths.

The strict wrapper receipt schema is an enriched controller record, not the raw merge-verifier output. It preserves raw `candidate_revision` and actual `revision`, binds graph/policy/input/fence plus candidate manifest and result digests, and permits no self-approval. The external verifier remains responsible for proving actual merge ancestry and checks at the candidate head; this module does not query GitHub. Neither a distinct merge SHA nor an equal fast-forward SHA is fabricated or inferred.

The previous 25 test methods remain, with their fixture tasks now explicitly declaring foundation kind/authority and receipts using separate candidate/merge fields. Eleven added methods cover claim/crash/restart before process binding, precommit rollback, positive no-launch proof and its stale/false variants, bound-process rejection of no-launch, distinct merge identities, exact sandbox-only/runtime-vs-code requirements and missing authority. All 36 methods await the root's fresh isolated execution at this revision; earlier test receipts do not qualify these changes.
## Pre-existing ledger admission

Before calling the reference Scheduler initializer, the wrapper now opens any existing regular ledger in SQLite read-only/query-only mode and requires its matching f11_mode and explicit f11_schema_version marker. The current wrapper schema version is 2 (durable launch attempts). Missing mode, missing/incompatible version, missing launch schema, empty files and malformed databases are refused before superclass schema setup, directory creation or chmod. New absent database paths initialize normally and record both markers; marked compatible databases can reopen without losing reservations.

No automatic adoption or migration is performed. In particular an old reference-scheduler database with RUNNING work remains byte/schema/row unchanged on refusal. An authorized migration must stop new claims, independently reconcile existing launch/process/outcome state, preserve reservations and backups, and only then establish reviewed mode/version metadata and attempt records. Merely writing a marker is not an approved migration. This task supplies no command to mark or migrate a live ledger.

Four additional tests preserve all prior 36 methods and check idle/active legacy-database refusal before superclass initialization, empty-file refusal, missing/incompatible version refusal, and compatible marked restart. Bytes, schema, rows, metadata and file mode are compared before/after rejected adoption. These are temporary SQLite fixtures for root's isolated executor, not changes to the actual controller.
