# F03 threat model v1.1 (2026-10-25)

Status: review candidate; design policy with offline synthetic tests. This document does not establish sandbox, staging or production qualification. Source baseline: a9aa1f1ef2b532a4c2a9f1c6e4ddc9861feac18b. F01 acceptance is supplied by the controller; F03 does not modify it.

## Scope and authority

The repository describes a planned system, not an installed site. `reference/mermaid/A00.mmd`, `A01.mmd`, `A02.mmd`, `reference/components/component_registry.json`, `reference/workflows/X01.json`, `V01.json`, and `I24.json` are design inputs. Existing `docs/security/THREAT_MODEL.md`, `CREDENTIALS_AND_CI.md`, `CONTAINER_AND_HOST_BASELINE.md`, `AGENTS.md`, and the execution protocol remain authoritative. Addresses, accounts, actual versions, VLANs, credentials and carrier settings are deliberately unspecified. No new production service is proposed.

Protected assets: contact and consent state; private inventory; application and tenant data; source/evidence integrity; credentials and recovery material; availability and provider budget; exact approval and external-action receipts. Adversaries include unauthenticated internet clients, malicious tenants, poisoned sources/dependencies/models, compromised application accounts, and malicious coding agents with arbitrary code execution. A compromised privileged host remains a residual risk; process separation is not a sufficient defense against it.

## Classification and data handling

Classification is enforced by explicit labels plus source owner review, not a regex claiming to recognize every secret. Unknown/unlabelled data is denied. Inheritance uses the most restrictive input classification; aggregates require reviewed reclassification, not automatic downgrading. The offline inheritance function selects the most restrictive known input and denies unknown/empty provenance. Its reclassification function permits only unchanged or stricter labels. Owner-reviewed downgrades remain explicitly unimplemented: F10/F16 with the data owner must define authenticated approval, provenance and independent verification; this candidate never accepts a downgrade.

| Class | Examples (categories only) | Allowed handling | Disclosure / retention |
|---|---|---|---|
| public | Already approved published copy | Public export only after owner approval; synthetic tests may use public content | Retain per publication owner; deletion follows source policy |
| internal | Sanitized engineering plans and synthetic fixtures | Restricted engineering store; synthetic public fixture needs explicit approval | Shared logs restricted to approved public/synthetic data; owner sets finite retention before deployment |
| confidential | Client assets, contact PII/consent, call recordings/transcripts, private inventory | Native owner app or authorized same-tenant private store; encryption/access audit; no general coding prompt, public issue or shared log | Minimize, redact before export; retention/deletion and legal holds need owner-approved site policy |
| restricted | Tokens, private keys, recovery material, unsanitized credential dumps | Secret manager/offline custody only; references in source, never values in logs/prompts | Rotate exposed secrets; recovery owner defines custody and destruction |

Synthetic fixtures must be constructed, not copied/redacted from actual customer records. Runtime owners remain Mautic for contacts/email permission, channel-specific ledger for telephone permission, native apps for their data, and PostgreSQL for operational receipts; this model does not create a duplicate CRM. Labelled confidential objects require matching authenticated tenant for access; restricted values are unavailable to this policy's callers.

## Control verification matrix and release gates

`policy.json` and `policy_checks.py` encode a deliberately narrow offline decision oracle. They are reviewable policy examples, not deployed middleware, a general URL filter, a network sandbox, or proof that labels/authentication are truthful. `test_policy.py` exercises rejection paths and legitimate synthetic controls. The test author is the implementer; an independent verifier is still required.

| Control | Offline evidence | Required enforcement evidence before qualification |
|---|---|---|
| C01 authenticated scoped authority | forged issue authority, unknown/missing role/capability denied | Trusted packet origin, hash/fence validation, no agent write to ledger; exact-head independent review |
| C02 no worker external effect | coding/build/model roles denied network and production action | IPv4/IPv6/DNS/proxy/VPN/link-local/metadata denial; denied host sockets, coordinator files, production credentials; verified resource and mount controls |
| C03 private data exclusion | unlabelled/restricted/confidential shared logs denied; cross-tenant access denied | Native app/API/object/cache/DB authorization tests and exported evidence secret/PII review |
| C04 webhook authenticity | valid synthetic HMAC accepted; forged, stale, future, wrong-tenant/source, scoped replay and oversized denied | Provider-specific raw-body signature algorithm, durable atomic replay protection, timing/rate limits, key rotation and error handling |
| C05 exact final action | mismatched tenant/revision/destination/channel/asset-set/action-scope, unknown channel, missing channel-specific eligibility or approval, unknown state and recovery HOLD denied | Independent authenticated human approval and current native eligibility/quota immediately at dispatch; provider receipt reconciliation |
| C06 approved outbound routing | only literal reviewed mock target allowed; IP/userinfo/redirect-style and unknown hosts denied | Broker enforcement on every resolved address and redirect, TLS identity, DNS-rebinding resistance; no bypass through proxy/env/native tools |
| C07 supply chain | build role cannot acquire extra capability | Digest/lock/SBOM provenance review, actual arbitrary build execution in isolated runner and malicious artifact import cases |
| C08 restore integrity | no resumed action while recovery is unverified | Generation/hash verification, isolated full restore, suppression/provider reconciliation, measured RPO/RTO and human release |

**Production-isolation blocker:** no attributable qualification receipt for this exact native adapter, host, mounts, network stack and production topology is present in this task input. The reported native probe established only selected canary reads/network requests were denied; it does not establish comprehensive native or production isolation. C02, T02 and T07 remain NOT_RUN at the required qualification level. Do not grant F03's sandbox-isolation acceptance item, G02, production enablement or any higher evidence level from this work. F06/F12 with an independent verifier must supply the matrix above in an authorized disposable environment. No probing of production is authorized here.

Other open facts: actual tenant partition configuration; retention periods and data jurisdiction; account/ruleset availability; application and provider versions; carrier test permission; backup/key custody and restore targets. Owners must supply and verify these facts in their scoped tasks. Residual risks include approved-upstream compromise, kernel defects, human approval compromise, parser defects, incomplete redaction and single-host outage. Any exception needs exact scope, owner, independent reviewer, expiry, compensating control and evidence; none is granted by this document.

## Runbook

1. Keep production/external effects disabled. Controller checks immutable source/input/fence bindings and path scope; reviewer examines changed files and source hash receipt.
2. Run `python -B docs/security/threat-model/test_policy.py` from this source snapshot. Read all failures; never change an expected denial just to pass. Tests use no network or production data.
3. Independent verifier reproduces offline tests, checks meaningful positive and negative cases, then separately qualifies real enforcement in the approved disposable environment. Record exact configuration/digests, targets (sanitized), UTC time, expected/observed outcomes and exit codes.
4. On exposure or suspected escape: stop scoped work, preserve minimal redacted evidence, notify configured private security owner; if F02 channel is absent, controller resolves that private channel. Rotate at authority and reconcile uncertain effects. Do not publish exploit details or restart shared infrastructure.
5. On failure or missing site input: HOLD the affected gate and assign the owner above; unrelated synthetic work may continue. Return candidate for independent review without self-acceptance. Reassess on topology, tenant, provider, model/tool, dependency, permission or recovery changes; increment this model's version.

## v1.1 independent-review remediation

F03-R01: dispatch now requires nonempty asset_set_hash and action_scope on both the request and approval, in addition to tenant/revision/destination/channel. Any mismatch or missing material binding denies. These synthetic strings are not asserted to be cryptographically validated content hashes; F04/X03 owns canonical contract/provenance enforcement.

F03-R02: only the explicitly modeled web/social/email/voice channels can pass, and eligibility_channel must match the request. All other channels are held pending a scoped policy addition; this does not declare other V7 channels unsupported by the overall design. The caller must provide fresh, authenticated channel-specific eligibility; the oracle does not query native consent or authenticate that assertion.

F03-R03: replay keys are (authenticated tenant, authenticated source system, event ID). The synthetic-default source keeps the original single-source fixture wire format; explicit source_system must match authenticated_source. Source identity is trusted adapter context tied to its signing key, not payload authority. The simplified signature still authenticates event ID, timestamp, tenant and raw body. No production provider protocol, source-key registry or atomic durable store is implemented. Regression tests exercise same IDs across both tenants and authenticated sources, and reject mismatched/empty sources.

Disclosure coverage: inheritance and denied downgrade cases now execute offline. Authenticated provenance, synthetic status and approved downgrade workflow remain unqualified owner work. The independent review's 576 synthetic single-label combinations are not the original 576 runtime acceptance cases and are never counted as runtime evidence here.
